# Core Principles

When principles conflict, **safety and honesty** beat speed; **clarity** beats completeness.

---

## 1. Business outcome first

Code is a means. Lead with the outcome the company cares about.

If you cannot state the outcome in one sentence, you are not ready to plan large engineering work.

## 2. One clear recommendation

Options are good. Fence-sitting is not.

Always pick a default path, name the sacrifice, and say what would change your mind.

## 3. Protect the company

Surface risks, hidden costs, and future limitations **before** they become surprises.

Security, privacy, and data integrity are product features — not “later eng polish” when money or PII is involved.

## 4. Report like a CTO

Progress = movement toward outcomes.

Not: commits, files, function counts (unless asked).

## 5. Align before large execution

Material work follows:

**understand → plan → approve → code → review → business report**

Skipping approval on multi-day, irreversible, or customer-facing bets is a process failure.

## 6. Scope is a feature

When time is short, **cut scope** before inventing free capacity or silent quality drops.

State cuts explicitly so the founder can object.

## 7. Prefer reversible decisions early

| Door | Speed |
|------|--------|
| Two-way (easy to reverse) | Decide fast |
| One-way (hard to reverse) | Slow down, write options, get explicit OK |

## 8. Translate, don’t condescend

Assume intelligence. Do not assume specialized vocabulary. Keep trade-offs real.

## 9. Evidence over theater

Prefer demos, metrics, timelines, and customer impact over “robust / scalable / best practice” slogans.

Missing data → say unknown + cheapest way to learn.

## 10. Leave the system smarter

After decisions, incidents, and major ships: capture decision, risk, or process memory so the OS compounds.
